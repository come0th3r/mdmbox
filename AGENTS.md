# MDMBOX — инструкции для работы в репозитории

## Начало сессии

1. Прочитать `PROJECT_MEMORY.md`: цель, ограничения, решения, статус и ближайшие действия.
2. Перед реализацией прочитать соответствующий этап `docs/BETA_ILYA_UPGRADE_PLAN.md`. Это подробный план и checklist приёмки.
3. Проверить текущие branch/HEAD, `git status` и staged diff. Память отражает последнюю проверку, а не гарантирует текущее состояние. Чужие изменения сохранять.
4. Продолжать с первого незавершённого пункта текущего этапа, учитывая последнюю задачу пользователя. Создание документации не означает выполнение реализации.

## Правила проекта

- Общаться с пользователем по-русски; имена кода и технических сущностей сохранять в стиле репозитория.
- Рабочая ветка обновления — `beta-ilya`, основная — `main`. Пользователь просит отправлять изменения через установленный Fork. При использовании bundled Git явно отличать CLI-операции от действий в GUI.
- Не использовать Python для новых изменений и автоматизации: рабочий план обходится без него, включая UI. Использовать C++/Qt, Go, PowerShell и HTML/CSS/JavaScript по назначению.
- Переиспользовать кодовую базу Nekobox, модели и RPC. Архитектурные предложения из плана не считать уже реализованными возможностями.
- Сохранять полный профиль mikan, порядок правил, DNS и proxy-группы; не объявлять поддержку протокола по одному успешному parsing.
- Для Figma сохранять точность исходного дизайна; assets хранить локально. Демонстрационные метрики не выдавать за реальные.
- Отмечать тесты как PASS только после выполнения. Невыполненные обязательные проверки — NOT RUN или BLOCKED с причиной.
- Слияние в `main` и stable release — только после release gates из плана. Не делать force push и не перемещать опубликованные теги.
- Коммитить только файлы текущей задачи. Не сохранять credentials, subscription tokens, реальные HWID и приватные пользовательские конфиги в git или память.

## Документация вызовов функций

- При добавлении или изменении вызова через UI/bridge/backend обновлять `docs/FUNCTION_CALLS.md` в том же коммите, что и код. При смене внутренней функции обновлять затронутую цепочку; не ограничиваться списком сигнатур.
- Для каждой цепочки указывать точку входа/событие, caller → callee, параметры и ограничения, return/signal/event, синхронность, ошибки и побочные эффекты (запись, сеть, процесс, настройки ОС).
- Отличать принятие команды в очередь от завершения, `SaveResult::changed` от `ok()`, существующий контракт от планируемого. Указывать ограничения, source paths и проверку/fixture; PASS только после выполнения.
- При изменении payload/requestId/событий одновременно согласовать producer и consumer и обновить примеры на synthetic данных. Не документировать реальные URL подписок, tokens, HWID или ключи.
- Для новых подсистем добавлять раздел или ссылку на профильную документацию из карты вызовов. Перед коммитом сверять имена функций и ссылки с исходниками; UI-разработчику начинать с `docs/UI_DEVELOPER_HANDOFF.md`.

## Поддержание памяти

После значимого этапа обновить `PROJECT_MEMORY.md`: что сделано, что проверено, какие блокеры остались и с чего продолжать. Флажки подробного плана менять только по подтверждённым результатам. Не дублировать весь checklist и не записывать предположения как установленные факты.
