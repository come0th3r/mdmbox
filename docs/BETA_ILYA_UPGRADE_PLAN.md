# MDMBOX: план обновления `beta-ilya`

Дата исследования: **14 октября 2026 года**.
Статус: **план реализации на основе исследования исходников и Figma**.
Целевая платформа: **Windows 10/11 x64**.
Рабочая ветка: **`beta-ilya`**. Основная ветка: **`main`**.

## Цель

Обновить MDMBOX так, чтобы приложение полноценно работало с подписками, клиентскими правилами и всем набором экспортируемых протоколов mikan, воспроизводило предоставленный интерфейс Figma и выпускалось воспроизводимой сборкой.

Последовательность работ:

1. **Этап 0 — исследование, воспроизводимая сборка и контракты.**
2. **Этап 1 — подписки mikan, протоколы, автоправила и тесты backend.**
3. **Этап 2 — самостоятельная pixel-perfect оболочка по Figma.**
4. **Этап 3 — соединение оболочки с backend и системными функциями.**
5. **Этап 4 — полные испытания, beta, слияние в `main`, релиз.**

Создание этого документа не означает завершение реализации или прохождение испытаний приложения. Флажки ниже отмечаются только после выполнения и сохранения доказательств.

### 1.2. Найденные препятствия

- `RawUpdater::updateClash()` извлекает прежде всего `proxies`; этого недостаточно для переноса `proxy-groups`, `rules`, `rule-providers` и DNS целого профиля mikan.
- `GroupUpdater::Update()` обновляет метаданные, а при `sub_clear` удаляет старые профили **до** завершения разбора нового ответа. Требуется транзакционное обновление.
- В `Group` есть URL, строка `info`, время обновления и порядок профилей; отдельной модели полного управляемого профиля и типизированных метаданных подписки пока нет.
- Оболочка ищет внешний каталог `newdesign`, включая жёсткий путь `C:/Users/0th3r/nekoray/newdesign`; в исследованной копии этого каталога нет. Интерфейс необходимо включить в репозиторий и установщик.
- В `mdmbox_shell_window.cpp` много внедряемого JavaScript и обновление страницы таймером 1200 мс. Вместо поиска элементов по тексту нужны стабильные компоненты, идентификаторы и события состояния.
- `go.mod` ссылается на соседние каталоги `libneko`, `sing-box`, `sing-quic`, `sing`. Их ревизии и получение требуется согласовать с `libs/get_source*.sh`; исходники зависимостей ещё не проверены полностью.
- `tools/build-local.ps1` содержит пути к Python чужого пользователя, изменяет `go.mod` при сборке и отключает проверки Go-сумм. Эти части следует заменить воспроизводимым bootstrap.
- Версии Qt в локальном скрипте и CI различаются; CI сохраняет старую матрицу Nekoray. Нельзя принимать утверждение README «latest stable» за доказательство реальной версии встроенного ядра.
- В `test/` найдены два build-smoke shell-скрипта; полноценную матрицу регрессионных, протокольных и визуальных испытаний ещё предстоит создать.

### 1.3. Контракт mikan

Исследована ревизия **`a7b32c3efdfe85fe2450940f876fbb27fcf11ecc`** от 13 октября 2026 года. Это зафиксированная база совместимости, а не обещание поддержать любую будущую версию.

Изучены `internal/panel/subs/{handler,apps,render,rules,routes,singbox}.go`, сопутствующие тесты и golden-файлы, README и `go.mod`.

- mikan строит серверную часть на **mihomo**; в исследованной ревизии зависимость — **v1.19.32**.
- Подписка выдаётся по пользовательскому URL с токеном; префикс пути может настраиваться. Не конструировать URL жёстко как `/sub/…`.
- Параметр `format` задаёт представление: `clash`/`mihomo`/`yaml`, `uri`/`v2ray`/`base64`, `singbox`/`sing-box`, `html`. Это не отменяет фильтрацию протоколов по User-Agent.
- `DetectApp()` и `Supports()` учитывают семейство и версию ядра. Просто дописать `?format=clash` к запросу старого Nekobox недостаточно.
- Метаданные: `Subscription-Userinfo`, `Profile-Title` с `base64:`, `Profile-Update-Interval`, `Support-Url`, `Profile-Web-Page-Url` и дополнительные operator/HWID-заголовки.
- `Profile-Update-Interval: 1` в этой реализации означает **один час**, чтобы клиент получил новый порт или REALITY target после серверной автоподстройки.
- Привязка устройств использует, в частности, `X-Hwid`, `X-Device-Os`, `X-Ver-Os`; отказ может приходить как специальный профиль-заглушка, а не только HTTP-ошибка.
- Полный sing-box export ориентирован на схему **1.12+** и не сохраняет возможности без эквивалента: например XHTTP, VLESS Encryption, отдельные mihomo-протоколы и некоторые виды правил.

**Для полного покрытия mikan основной путь — исполнять его Clash/mihomo-профиль через совместимую закреплённую версию mihomo, а не сводить всё к URI или конвертировать всё в старый sing-box.**

### 1.4. «Автоправила»: три разных механизма

1. **Клиентская маршрутизация панели:** режимы `all`, `ru_direct`, `blocked`, пользовательские правила, списки провайдеров, proxy-группы и DNS. Их переносит полный профиль подписки.
2. **Автовыбор сервера:** группы `url-test`/`fallback` и другие группы из профиля. Их семантика сохраняется, а выбранный фактический сервер отражается в интерфейсе.
3. **Серверный autotune:** mikan меняет порт или параметры REALITY на своей стороне. Клиент вовремя получает обновление и безопасно переподключается; алгоритм управления сервером не переносится в desktop-приложение.

Happ/INCY имеют отдельный формат доставки routing. Он не заменяет полноценный профиль mihomo и не должен становиться скрытой обязательной зависимостью MDMBOX.

## 2. Целевая архитектура и языки

```text
HTML / CSS / JavaScript — локальная оболочка по Figma
                 │ QWebChannel: команды и события
C++17 / Qt 6 — сервисы приложения и модели Nekobox
  ├─ SubscriptionService: загрузка, метаданные, расписание, commit/rollback
  ├─ ManagedProfileService: профиль панели, правила, локальные overrides
  ├─ ProfileRepository: старые профили и новые managed profiles
  └─ CoreManager → адаптер выбранного ядра
       ├─ mihomo: полный профиль mikan, TUN/DNS/routes
       ├─ nekobox_core / sing-box: совместимость со старыми профилями
       └─ Xray: существующие специальные профили
```

- C++/Qt управляет приложением, хранением, подписками, жизненным циклом ядер и системными настройками.
- Ядра остаются на Go. Не переписывать сетевые протоколы на C++.
- Для интерфейса использовать существующее направление **Qt 6 WebEngine + локальные HTML/CSS/JavaScript**. Отдельный browser-preview запускается с mock-bridge, production — с QWebChannel.
- Имена сервисов в схеме — целевые границы ответственности; окончательные файлы определяются после выделения существующей логики. Не заводить параллельные независимые базы данных.
- Один активный владелец TUN, DNS и системных маршрутов. Смена ядра: остановка → освобождение ресурсов → запуск → подтверждение готовности → публикация connected. Не включать два TUN одновременно.
- mihomo запускать управляемым отдельным процессом с локальным API, ограниченным loopback и авторизацией. Клиентский UI не получает прямого доступа к API ядра или subscription token.
- Полноценный нативный UI на C++/Qt Widgets или C++/QML тоже возможен, но его выбор потребует другого renderer и повторного переноса макета. Базовый план сохраняет уже существующий WebEngine-мост.
- **Python не используется** в новых исходниках, runtime, тестах и собственных build/release-скриптах. PowerShell — автоматизация Windows, Go — сетевые тестовые стенды, Node.js — визуальные тесты.
- Использовать готовый Qt SDK. Если сборка сторонней зависимости из исходников требует Python, сначала найти подходящий готовый артефакт; не добавлять такую зависимость незаметно.
